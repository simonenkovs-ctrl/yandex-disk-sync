Обзор проекта
Яндекс Диск Синхронизатор для Android — нативное приложение (Kotlin 2.0 + Jetpack Compose + Material 3) для синхронизации локальных папок смартфона с Яндекс Диском.

Что уже реализовано (текущее состояние, версия 1.3.5)
REST-клиент (api/YandexDiskClient.kt): OkHttp 4.12, ретраи 429/5xx с exponential backoff, readTimeout(0) для больших файлов (MP4), стриминговые upload/download с прогрессом.
Движок синхронизации (engine/SyncEngine.kt): 3 режима (TWO_WAY, UPLOAD_ONLY, DOWNLOAD_ONLY), MD5-хеширование потоком, фильтрация мусора, сжатие фото (PhotoCompressor) в UPLOAD_ONLY.
Хранилище: Room SQLite (file_records), AppPreferences (SharedPreferences + Gson, реактивный StateFlow).
Фон: Foreground Service (SyncForegroundService) с WakeLock/WifiLock, DailySyncWorker (WorkManager, ежедневно, условия Wi-Fi/зарядка), автообновление через GitHub Releases.
UI: 4 экрана (Главная, Папки, Журнал, Настройки) на Compose.
v1.3.5: BackupManager (автобэкап настроек/папок), allowBackup=true, защита от повторной загрузки сжатых фото на чистой БД.
Статус репозитория
Ветка android, remote: simonenkovs-ctrl/yandex-disk-sync.
Рабочее дерево содержит незакоммиченные/неотслеживаемые каталоги сборки: apk_v133/, apk_v134/ (и, судя по структуре, аналогичные apk/, apk_v123/, apk_v124/). Это артефакты, которые, вероятно, должны попасть в .gitignore, а не в git.
CI: .github/workflows/build-apk.yml собирает release APK на push.

B. Исправление потенциальных багов (приоритет: высокий)
Кэш логов растёт неограниченно в памяти: в SyncEngine.log() список ограничен 200 элементами — это нормально. Но logsFlow стартует пустым при каждом запуске приложения (логи не персистятся). Если нужно видеть прошлый запуск — добавить персистентность лога (Room-таблица или файл).
syncFolderPair при сбое API падает в finally некорректно: внутри syncAll()/syncSingleFolder() ловят общее исключение, но состояние папки помечается «Успешно» только при отсутствии isCancelled. Проверить: при SyncMode.TWO_WAY обновление с record == null и включённым syncDeletions может неожиданно удалить локальные файлы. Стоит добавить dry-run/предпросмотр удалений.
computeLocalMd5/computeFileMd5 возвращают пустую строку при ошибке — далее это тихо сравнивается. Лучше логировать ошибку и явно решать, пропустить файл или падать.
Потокобезопасность isCancelled: isCancelled — var Boolean без @Volatile, но читается/пишется из разных корутин (IO и UI). Потенциальная гонка. Пометить @Volatile.
Сжатие фото и сравнение размеров: в handleUploadOnly для случая record == null и сжатия используется remoteRes.size <= localSize как эвристика «уже загружено». Может ложно срабатывать на совпадении размеров. Уже частично покрыто фиксом v1.3.5 — стоит покрыть юнит-тестом.
C. Новые функции и улучшения (приоритет: средний/низкий)
Тесты: проект полностью без тестов (test/ и androidTest/ пустые, только testInstrumentationRunner). Добавить:
Unit-тесты: isIgnored, formatBytes, isNewerVersion, isIgnored-список, разбор версий.
Тесты AppUpdater.isNewerVersion и PhotoCompressor (если выделить чистую логику).
Логика «синхронизации удалений»: добавить настройку подтверждения/диалог перед массовым удалением файлов в TWO_WAY, чтобы избежать случайных потерь.
Параллельная синхронизация папок: сейчас папки обрабатываются последовательно. Можно распараллелить с ограничением по конкуренции (coroutines Semaphore), но осторожно с лимитами API Яндекс Диска (429).
Возобновление прерванной загрузки (resume broken upload): сейчас uploadFile начинается заново при ошибке. Яндекс Диск поддерживает Range/возобновление для больших файлов — можно оптимизировать для видео.
